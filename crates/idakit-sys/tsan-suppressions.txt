# init_library() takes an SDK-internal mutex once and never releases it; close_database()
# later takes a second one while that first is still held, inside libida.so. idakit only ever
# runs one kernel thread, so this can never actually deadlock.
deadlock:bring_up_kernel
deadlock:guarded_close

# IDA's own exit teardown runs on the main thread and frees mutexes and heap that a worker
# thread libida spawned inside open_database is still using; libida never joins it and offers
# no way to reach it. Both sides are IDA's own memory, raced after idakit's kernel thread has
# stopped: `Database` is !Send with no `Drop`, so idakit's only close runs on that thread.
race:qmutex_free
race:qrealloc

# Same exit-teardown race, surfacing as a mutex-invalid-use report instead of a plain race: a
# freed mutex's memory gets reused, so a worker thread's late qmutex_lock/qmutex_unlock lands on
# what TSan sees as a freshly "created" or already-destroyed mutex, both frames entirely inside
# libida.so. Seen once in CI on 2887373 -- a commit with no code path anywhere near decode_sweep
# or the kernel -- and only after decode_sweep's own assertions had already passed; 7/7 clean
# local reruns since (2x full `just sanitize thread`, 5x direct binary). idakit never calls
# qmutex_lock/qmutex_unlock itself (grep confirms), so this is libida's own teardown hazard, not
# ours to fix.
mutex:qmutex_lock
mutex:qmutex_unlock
